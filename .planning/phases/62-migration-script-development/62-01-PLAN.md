Create `scripts/migrate-consolidate-models.ts` following the pattern from `scripts/backfill-retroactive-predictions.ts` (dotenv/config, getDb, process.argv CLI).

**CONSOLIDATION_MAP** (3 models that have both Synthetic and base IDs in MODEL_PROVIDER_ROUTES):
```typescript
const CONSOLIDATION_MAP: Record<string, string> = {
  'deepseek-r1-0528-syn': 'deepseek-r1',
  'kimi-k2-thinking-syn': 'kimi-k2-thinking',
  'kimi-k2.5-syn': 'kimi-k2.5',
};
```

**Important:** Only these 3 models consolidate. The other 10 Synthetic-only models (deepseek-v3-0324-syn, deepseek-v3.1-terminus-syn, etc.) are Synthetic-exclusive and will be renamed in Phase 63 (CONS-03/04), not Phase 62.

**CLI flags:** Parse `--dry-run` and `--verbose` from process.argv (simple check, no yargs needed since only 2 flags).

**Migration flow (all within a single PostgreSQL transaction):**

1. **Pre-validation phase:**
   - Count total rows per table (predictions, llm_model_stats, bets, model_balances, model_usage)
   - Count affected rows per table (rows with model_id in CONSOLIDATION_MAP keys)
   - Detect duplicate conflicts in predictions: matches where both old and new model_id exist (e.g., match predicted by both 'deepseek-r1-0528-syn' AND 'deepseek-r1'). Use GROUP BY match_id, consolidated_model_id HAVING COUNT > 1
   - Detect duplicate conflicts in other tables (llm_model_stats: same date+consolidated_model, bets: same match+consolidated_model+type, model_balances: same consolidated_model+season, model_usage: same date+consolidated_model)
   - Print summary of conflicts found

2. **Deduplication phase (predictions table):**
   - For each entry in CONSOLIDATION_MAP:
     - Find matches where BOTH old_id and new_id have predictions
     - For each conflicting match: keep the prediction with the NEWER created_at (deterministic precedence: newest wins). If created_at is identical, keep the one with the base model_id (not -syn).
     - DELETE the losing prediction using ROW_NUMBER() OVER (PARTITION BY match_id ORDER BY created_at DESC, CASE WHEN model_id = new_id THEN 0 ELSE 1 END) — row number 1 is kept, others deleted
     - Track count of deleted predictions per model pair

3. **Deduplication phase (other tables):**
   - llm_model_stats: For same (date, consolidated_model_id), merge by summing counts (success_count, failure_count, total_attempts, timeout_errors, parse_errors, api_errors, language_errors, other_errors), recalculate success_rate, keep the newer updatedAt. Delete the -syn row after merging.
   - bets: For same (match_id, consolidated_model_id, bet_type), keep newest created_at, delete older.
   - model_balances: For same (consolidated_model_id, season), sum balance/totalBets/winningBets, keep newer updatedAt. Delete -syn row.
   - model_usage: For same (date, consolidated_model_id), sum predictions_count/total_cost, keep newer updatedAt. Delete -syn row.

4. **UPDATE phase:**
   - UPDATE predictions SET model_id = new_id WHERE model_id = old_id (for each mapping)
   - UPDATE llm_model_stats SET model_id = new_id WHERE model_id = old_id
   - UPDATE bets SET model_id = new_id WHERE model_id = old_id
   - UPDATE model_balances SET model_id = new_id WHERE model_id = old_id
   - UPDATE model_usage SET model_id = new_id WHERE model_id = old_id
   - Track row counts for each UPDATE

5. **Post-validation phase:**
   - Re-count total rows per table (should equal pre-count minus deduplicated)
   - Check for orphaned foreign keys: predictions.model_id NOT IN models.id (EXPECTED to find some — Phase 63 updates models table)
   - Check unique constraints: no duplicates in (match_id, model_id) for predictions, (date, model_id) for llm_model_stats, etc.
   - Print validation results with PASS/FAIL for each check
   - Explicitly note that orphaned FK in predictions is EXPECTED pre-Phase 63

6. **Commit/Rollback:**
   - If dry-run: ROLLBACK and print "DRY RUN: All changes rolled back"
   - If not dry-run AND all validation checks pass (except expected orphaned FKs): COMMIT
   - If validation fails: ROLLBACK and print error details

**Idempotency:** The script is safe to re-run. If no rows match old model_id, deduplication deletes 0, UPDATE affects 0. Pre-validation will show "0 affected, 0 conflicts".

**Console output:** Use clear phase headers with counts. Example:

**ROLLBACK_MAP** (reverse of CONSOLIDATION_MAP):
```typescript
const ROLLBACK_MAP: Record<string, string> = {
  'deepseek-r1': 'deepseek-r1-0528-syn',
  'kimi-k2-thinking': 'kimi-k2-thinking-syn',
  'kimi-k2.5': 'kimi-k2.5-syn',
};
```

**CLI flags:** `--dry-run` and `--verbose`.

**Rollback logic:**

1. **Safety check:** For predictions table, ONLY restore -syn IDs where `provider_used` matches the Synthetic provider ID. This prevents restoring -syn IDs for Together AI predictions that legitimately used the base model_id.
   ```sql
   UPDATE predictions SET model_id = 'deepseek-r1-0528-syn'
   WHERE model_id = 'deepseek-r1'
     AND provider_used = 'deepseek-r1-0528-syn'
   ```

2. **For predictions with NULL provider_used** (pre-Phase 61 historical data): Leave as-is. Cannot determine original provider without attribution data. Log count of NULL provider_used rows that were NOT rolled back.

3. **For other tables** (llm_model_stats, bets, model_balances, model_usage): These don't have provider_used. Reverse ALL rows where model_id = consolidated_id AND the -syn model previously existed. Since Phase 62 forward migration merged/summed stats, the rollback cannot perfectly un-merge aggregates. Document this limitation:
   - llm_model_stats: Rollback UPDATE model_id back to -syn, but merged aggregate values remain summed (cannot split)
   - bets/model_balances/model_usage: Same — UPDATE model_id back, but summed values stay
   - Note in output: "Aggregated values cannot be un-merged. Manual adjustment may be needed."

4. **Pre-rollback validation:** Count rows that would be affected per table.

5. **Post-rollback validation:** Verify no orphaned FKs, unique constraints intact.

6. **Transaction:** Same BEGIN/COMMIT/ROLLBACK pattern as forward migration. Dry-run support.

**Console output:** Same clear format as forward migration with rollback-specific messaging.

**Important notes in script comments:**
- Rollback is NOT a perfect inverse of forward migration (aggregates cannot be un-merged)
- Rollback is primarily for predictions table where provider_used enables safe reversal
- If Phase 63 has already run (models table updated), rollback will create orphaned FKs in reverse direction
- Rollback should be run BEFORE Phase 63, not after
